# AWS 태그 규약 — ISMS-P 1.2.1 자산 식별용

**이 문서는 자산을 운영하는 부서가 읽는 문서다.** 개발자용 상세 매핑은 [`field-mapping.md`](field-mapping.md) §2에 있다.

---

## 왜 태그인가

AWS API로 얻을 수 있는 것은 기술 속성뿐이다. 인스턴스 타입, IP 주소, 암호화 설정.
그런데 자산관리대장이 요구하는 칸의 절반은 **조직 정보**다.

```
관리부서 · 관리책임자 · 용도 · 개인정보 보유 여부 · 인증범위 포함 여부 · 정보 민감도
```

"이 서버 담당자가 누구냐"에 답하는 AWS API는 없다. 조직 정보가 AWS 안에 존재할 수 있는
유일한 통로가 태그다. 그래서 이 도구의 전제는 하나다.

> **태그 규칙을 세우고 지키면 자산 관리가 자동화된다. 안 지키면 자동화가 안 된다.**

태그를 한 번 달면 그 뒤로는 매 실행마다 자동으로 대장에 채워진다. 한 번 투자하면 끝나는 일이다.

## 태그 키 14종

**●** 필수 · **조건부** 아래 조건일 때만 필수 · **○** 선택

| 태그 키 | 허용값 | 대장 컬럼 | 붙이는 주체 | |
|---|---|---|---|---|
| `Name` | 네이밍 규칙 준수 문자열 | 호스트명 / 자산명 | 자산 운영 부서 | ● |
| `OwnerDept` | 부서명 | 관리부서 | 자산 운영 부서 | ● |
| `OwnerManager` | 실명 또는 사번 | 관리 실무자(운용자) | 자산 운영 부서 | ● |
| `OwnerResponsible` | 실명 또는 사번 | 관리 책임자 | 자산 운영 부서 | ● |
| `InventoryCategory` | `WebServer` `WAS` `DB` `Batch` `Bastion` `CICD` `Monitoring` `Log` `Backup` `Auth` `File` `Gateway` | 용도(목적 및 기능) | 자산 운영 부서 | ● |
| `Environment` | `Prod` `Stg` `Dev` `Test` `DR` | (등급 룰 입력) | 자산 운영 부서 | ● |
| `ServiceName` | 서비스/시스템 명 | 소속 시스템 | 자산 운영 부서 | ● |
| `InScope` | `Y` `N` | 인증범위 포함 여부 | 정보보호 담당 | ● |
| `HandlePI` | `Y` `N` | 개인정보 보유 여부 | 개인정보보호 담당 | ● |
| **`DataClass`** | `public` `internal` `confidential` | 정보 민감도 | 자산 운영 부서 + 정보보호 담당 | ● |
| `PIItems` | `name,phone,email,rrn,card` (쉼표 구분) | 개인정보 항목 | 개인정보보호 담당 | 조건부 |
| `DataSource` | `Self` `ThirdParty` `Entrusted` | 수집 출처 | 개인정보보호 담당 | 조건부 |
| `ScopeReason` | 자유 문자열 | 제외 사유 | 정보보호 담당 | 조건부 |
| `SeverityLevel` | `1`~`5` | (참고값) | 자산 운영 부서 | ○ |

### 조건부 규칙

```
HandlePI = Y  →  PIItems 필수, DataSource 필수
InScope  = N  →  ScopeReason 필수
```

개인정보를 다루지 않는 자산까지 "개인정보 항목 미입력"으로 세면 숫자가 부풀어
우선순위가 뒤집힌다. 그래서 조건이 맞을 때만 필수로 센다.

---

## `DataClass`와 `HandlePI`는 다른 축이다

합치면 안 된다. **"내부용이면서 개인정보를 포함하는 자산"을 표현할 수 없게 되고,
그런 자산이 개인정보 보유 목록에서 조용히 빠진다.**

| | `HandlePI=N` | `HandlePI=Y` |
|---|---|---|
| `DataClass=public` | 홈페이지 이미지 | (모순. 검토 대상) |
| `DataClass=internal` | 내부 위키 | **회원 통계 — 누락되기 쉬운 칸** |
| `DataClass=confidential` | 소스코드·설계도 | 회원 DB |

`DataClass` 값 기준:

- **`public`** — 조직 외부인이 접근·열람해도 되도록 설계된 정보
- **`internal`** — 조직 구성원만 접근해야 하는 정보
- **`confidential`** — 지정된 담당자만 접근해야 하는 정보

## 태그를 어디에 붙여야 하나

**태그를 붙일 수 있는 모든 자원에 붙인다.** 특히 놓치기 쉬운 것:

| 자원 | 왜 놓치는가 |
|---|---|
| **EBS 스냅샷 · AMI** | 자동 생성되는 경우가 많아 수천 건씩 쌓인다. 그런데 원본과 같은 정보를 담고 있다 |
| VPC · 서브넷 · 보안그룹 · EIP | "네트워크는 자산이 아니다"라고 오해하기 쉽다. 안내서 자산유형에 포함된다 |
| EBS 볼륨 | 서버에만 태그를 달고 붙은 디스크는 빠뜨린다 |

> 스냅샷·AMI가 이 도구의 데모에서 전체 자산의 98%를 차지한다. 자동 생성 자원에
> 태그를 상속시키지 않으면 대장의 대부분이 빈 칸이 된다.

## 태그를 강제하는 방법

| 시점 | 방법 | 성격 |
|---|---|---|
| **생성 전** | Organizations 태그 정책 / CloudFormation·Terraform 기본 태그 / IAM 리소스 수준 조건 | 안 붙이면 생성 차단 |
| **생성 후** | AWS Config `required-tags` 룰 / Resource Groups 준수 보고서 / **이 도구의 갭 리포트** | 미준수 발견 |

**주의 — 태그 정책만으로는 부족하다.**
AWS 태그 정책은 *정의되지 않은 태그나 태그가 아예 없는 리소스를 준수 평가 대상으로 보지 않는다.*
즉 **태그가 하나도 없는 리소스는 태그 정책으로 잡히지 않는다.** 그 공백을 메우는 것이
이 도구의 갭 리포트다.

같은 이유로 수집기는 `resourcegroupstaggingapi.get_resources()`를 자산 목록의 근거로 쓰지 않는다.
그 API는 **태그가 전혀 없는 리소스를 응답에 포함하지 않는데, 그게 바로 우리가 찾는 대상**이기 때문이다.

```
전수 목록 = 서비스별 describe_* 결과의 합집합    ← 진실
태그 목록 = get_resources() 결과                 ← 보조
갭        = 전수 목록 − 태그 목록                ← 갭 리포트 1행
```

## 태그를 달면 어떻게 되나

수집기는 값이 없을 때 **왜 없는지**를 함께 기록한다. 태그 미입력은 이렇게 나간다.

```json
"owner_dept": { "value": null, "reason": "TAG_ABSENT",
                "hint": "OwnerDept 태그를 달면 다음 실행부터 자동 수집됩니다" }
```

`TAG_ABSENT`는 **담당자가 고칠 수 있는 유일한 사유**다. 갭 리포트의 "② 태그 미입력"이
이것이고, 태그를 달면 다음 실행부터 사라진다.

나머지 사유(`PERMISSION_DENIED` · `COLLECT_ERROR` · `OUT_OF_SCOPE`)는 태그로 해결되지 않는다.
권한 문제이거나 수집기를 확장해야 하는 일이다.
